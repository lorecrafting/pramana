### What is missing, in the order FR-10 needs it

1. **Quiescence is asserted, not proved.** `issuer_quiescent` is a plain string. The only
   check is `payload.quiescence_epoch == claim.writer_epoch` (`:1919-1921`), and
   `reclaim_claim` accepts the same token (`:1455`). R1 requires proof that "the old worker
   and delivery channel cannot still perform it", followed by an inspection of the external
   outcome (`WORKFLOW-CONTRACT.md:353-355`).
2. **The delivery channel is not recorded.** `channel` is always the literal
   `"protected-gateway"` (`:1290`, `:1918`). Nothing records which backend session or
   process an effect was delivered over.
3. **Nothing reconciles at boot.** No code lists `issued`, `unknown` or
   `reconciliation_required` claims when the Gateway starts. The contract's boot order
   (`WORKFLOW-CONTRACT.md:363-364`) has no code step between "new epoch" and scheduling.
4. **An `issued` claim can leave `issued` only through a receipt from its original issuer.**
   `settlement_provenance` requires `authenticated_actor == effect.issuer` (`:1917`). Nothing
   defines whether a successor reconciler counts as the same actor (Q2).
5. **No operation is designed to take a claim out of `reconciliation_required`.** No operation
   targets that state. A claim leaves it only incidentally (Q3).
6. **There is no execution record.** None of the `root_*` tables holds executions
   (`durable_store/database.ex:20-210`). R4's execution lifecycle exists only in the kernel
   reducer, where `worker_closed` "records closure rather than verifying it" (O0 row E6,
   `orchestrator/O0-AUTHORITY-INVENTORY-2026-09-22.md:81`).
7. **The encoder cost (A8) is unchanged.**

## 3. The live path today

O0 §1 found that the Coordinator **never calls `Gateway`**: it appends to JSONL
(`orchestrator/O0-AUTHORITY-INVENTORY-2026-09-22.md:25`). Three further facts, checked at
`e608a2b0`:

- **Nothing in production calls `effects/launch.ex` or `effects/prompt_delivery.ex`.** Only
  their own tests use them (`foundry/test/pramana_foundry/effects/launch_test.exs`,
  `prompt_delivery_test.exs`). Both write intent and completion checkpoints to the JSONL
  `Checkpoint`, not to the protected store. On recovery, `launch.ex` inspects the backend and
  adopts a matching agent (`effects/launch.ex:25-104`). `prompt_delivery.ex` looks for the
  prompt in the transcript as evidence of delivery (`effects/prompt_delivery.ex:25-73`).
- **The launch and prompt that actually run are in `AgentServer`.** It calls
  `Adapter.start_agent` (`agent_server.ex:548-567`) and `Adapter.prompt` (`:678-683`; the
  correction prompt at `:284`) directly, with no intent, claim or receipt. `AgentServer` is
  `restart: :temporary` (`:10`) under a `DynamicSupervisor` (`application.ex:46-49`). The
  Coordinator does not monitor it: neither `coordinator.ex` nor `agent_server.ex` calls
  `Process.monitor`. The Coordinator learns of an exit only from the message the worker
  sends in `terminate/2` (`agent_server.ex:430-462`), and a hard kill skips `terminate/2`.
- **Restart is contained, not reconciled.** If any assignment is `dispatched`, `crashed`,
  `cleanup_pending` or `cleanup_blocked`, boot enters `recovery_required`
  (`coordinator.ex:162-167`, `:1236-1243`). The re-enqueue path that zeroes `launch_retries`
  (`:1551-1600`) therefore cannot fire for those statuses. FR-10 replaces this containment
  with reconciliation, and must not reopen that re-enqueue path.

## 4. The line between Core and the controller

The operator-approved O1 rule is to write against execution identity and to **add no new
role-named protected vocabulary** (`orchestrator/O1-SEQUENCING-PROPOSAL-2026-09-23.md:41-43`,
`:57-59`). The protected items spec adds that "a guarantee Core owns must not depend on a
controller choosing to check it" (`fr-08/FR08B-PROTECTED-ITEMS-SPEC-2026-09-23.md:11-15`).

The boundary's effect protocol runs in this order:

1. The controller proposes an effect.
2. Foundry verifies it.
3. Foundry claims and issues it.
4. The adapter dispatches it.
5. The result is an exact receipt, a known non-start or failure, or unknown.

"A timeout is not permission ... to invent another effect ID" (`ORCHESTRATOR-BOUNDARY.md:479-505`).

| Core (protected, no roles) | Controller (the kernel today) |
|---|---|
| An execution record keyed by `execution_id` under `(scope, ticket, attempt)`, with R4's lifecycle states and legal moves (`:390`) | Which role an execution plays, and what its closure means for the ticket (`developer_closed` vs `reviewer_closed`, O0 E6) |
| Records the channel at issue. Requires quiescence evidence for `non_started`, for reclaim and for a retry | Decides when to propose a retry, and which alternatives apply at the limit (O0 seam 2, `:256`) |
| A boot reconciler that lists outstanding claims, observes each, and settles it or leaves it unknown | Scheduling after reconciliation |
| Receipt settlement, quarantine, and the exit from quarantine | Mapping receipts to domain events |

The role column already in the semantic key (`protected_primitives.ex:3376`, `:3399-3400`)
stays, and nothing new keys on it.

## 5. Proposed design

**D1. Executions become protected records.** Add a protected `root_executions` table with
`execution_id, scope, ticket_id, attempt_id, status, channel, revision`. It needs a schema
v4, added the same additive way `close_attempt` added v3 (spec `:70-73`). The rules:

- `create_effect` for a launch opens the execution as `pending`.
- The launch's `settle_claim` moves it: `succeeded` → `running`, `non_started` → `closed`,
  `unknown` → `unknown`.
- A new `close_execution` operation moves `running` or `unknown` to `closed`, and only with
  termination evidence.
- `close_attempt` also requires every execution under the attempt to be `closed`.

The table has no role column.

**D2. Record the channel at issue.** `issue_claim` gains a `channel` field naming what the
adapter will deliver over: the backend session or process identity, as FR-09 defines it.
Every receipt must name the same channel.

**D3. Quiescence needs evidence, not a token.** `issuer_quiescent` requires an observation
record that names the channel and shows one of two things:

- The channel's owner epoch is fenced: a successor holds the Gateway `Owner` lock, and the
  old worker's OS identity is observed gone. That observation uses FR-04's corrected
  `ProcessGroup` predicate (`REPAIR-PLAN.md:641-651`).
- The backend reports a terminal state through FR-09's `reconcile` operation.

What counts as evidence for each backend is FR-09's measurement to make. Core checks only the
record's shape and that it binds to `claim.writer_epoch` and `channel`.

**D4. The reconciler acts as successor issuer.** At boot, after the new epoch and before any
claim, a Core reconciler lists every claim in `issued`, `unknown` or `reconciliation_required`
and asks the adapter's `reconcile` operation about each one's channel. Then it settles:

- An exact receipt settles with that receipt's outcome.
- A non-start proved with D3 evidence settles as `non_started`.
- Anything else settles as `unknown`, and the holds stay.

It settles as an actor authorized for recovery (Q2). The controller sees only settled facts.

**D5. Monitors.** Each issued operation gets one monitored worker, watched with
`Process.monitor` by its owner instead of relying on a message from `terminate/2`. A `:DOWN`
settles nothing; it only queues a reconcile for that claim. Coordinator loss goes through
the D4 path.

**D6. Migration.** Route `AgentServer`'s `start_agent` and `prompt` through
`create_effect → claim → issue → adapter → settle_claim`. The adopt logic in
`effects/launch.ex` and the transcript-evidence logic in `effects/prompt_delivery.ex` become
the `reconcile` observers, reading protected claims instead of JSONL checkpoints. The JSONL
checkpoints are then deleted, not kept alongside.

**D7. Encoder (A8).** Replace the per-codepoint binary build with a scan that copies runs of
unescaped bytes. Measure before and after on the `OperationalStorageTest` padded commit.

## 7. Model before code: recommended, in Quint, kept small

**Model and results:** [`foundry/spec/fr10/README.md`](../../spec/fr10/README.md).

Earlier sessions recommended a model, and this proposal agrees. The risk lies in the
interleavings, not in individual guards. R1's six interleavings
(`WORKFLOW-CONTRACT.md:330-337`), multiplied by the crash points and the late receipts, are
too many to enumerate by hand. Batch C's reviews have also blocked on reachable sequences
that the tests did not name (`REPAIR-PLAN.md:452`).

**Scope:** one ticket and attempt, one semantic operation with ordinals 0..1, two epochs, and
one reservation of one unit.

- **Variables:**
  - `effect[e].status`
  - `claim[c].{status, epoch}`
  - `reservation[r].status`
  - the ledger `{available, held, consumed}`
  - `epoch` and `issuerAlive[epoch]`
  - `channelInFlight`: the set of deliveries in flight
  - `receiptsInFlight`: a bag, so receipts can duplicate and reorder
  - `external[e]`: one of `none`, `started`, `done`
  - `receipts[c]`: the receipt log
  - `execution[x].status`
- **Actions:** create, claim, issue, deliver, external start and finish, emit receipt,
  settle, cancel (with each proof), reclaim, epoch takeover, reconcile, close_execution,
  close_attempt, and create a retry.
- **Failures injected:**
  - a Gateway or Coordinator crash after any action (new epoch, in-memory state lost)
  - a hard kill of a worker
  - an old-epoch worker that keeps delivering after takeover
  - duplicate, late and conflicting receipts
  - a lost reply
- **Invariants:**
  - **I1:** at most one `external` start per claim and per semantic `(generation, ordinal)`.
  - **I2:** `available + held + consumed` stays constant.
  - **I3:** a `released` reservation implies `external[e] = none` forever.
  - **I4:** each reservation settles once.
  - **I5:** a claim in `unknown` or `reconciliation_required` keeps its unit and its leases held.
  - **I6:** a retry effect exists only when its predecessor is `non_started`, `failed` or `cancelled`.
  - **I7:** an old-epoch receipt changes only its own claim.
  - **I8:** after `close_attempt`, every execution is `closed` and no external action is pending.
- **Liveness:** with a fair channel and an issuer that eventually goes quiescent, every
  `issued` claim eventually leaves `issued`.
- **Size:** about 200–300 lines of Quint. The state space is small enough for `quint verify`
  (Apalache) or TLC to finish in minutes.

Settle one targeted question first: can `reconciled_settlement` (`:1903-1905`) take a
quarantined claim to a terminal state on any fresh receipt (Q3)?

The model is worth writing only if it covers D1–D5, not just today's primitives. It then
serves as the design check for commits 2–5, and each invariant becomes a named test.

## 8. Open questions for the operator

- **Q1. The FR-09 dependency.** D3 and D4 need FR-09's `reconcile` operation and its
  per-backend quiescence evidence. Should commits 1–5 proceed against a fake adapter before
  FR-09 closes, or wait?
- **Q2. The recovery actor.** Settlement requires the original issuer (`:1917`). Should the
  boot reconciler settle as that actor after epoch takeover? Or as a separate root recovery
  principal, under the "root's pre-existing safety-recovery authority" of R1
  (`WORKFLOW-CONTRACT.md:347`)?
- **Q3. The quarantine exit.** Today, a fresh receipt after an unknown-only history appears to
  settle a quarantined claim (`:1903-1905`). No test confirms this. Should leaving
  `reconciliation_required` require an explicit operator recovery record instead?
- **Q4. Executions in Core (D1).** Should Core get a protected execution table, or should the
  execution lifecycle stay in the kernel only, with Core checking effects alone? D1 is the
  reading that follows from the O1 rule. It costs a schema v4 and a re-attestation.
