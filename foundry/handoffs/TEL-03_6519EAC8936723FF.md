## Assignment

Fix `PramanaWeb.Telemetry.metrics/0` — six of eight domain metrics silently collected zero data because `Telemetry.Metrics` infers the event name from the metric name by replacing `.` with `:`, and the inferred names did not match the emitted events.

## Defect

Every domain event is emitted at the correct event name:
- `[:pramana, :retrieval, :search]`
- `[:pramana, :guard, :check]`
- `[:pramana, :mcp, :tool]`
- `[:pramana, :bake, :work]`
- `[:pramana, :acquire, :fetch]`
- `[:pramana, :coverage, :caveat]`

But `Telemetry.Metrics` derives event names from metric names by replacing `.` delimiters with `:`. So `summary("pramana.retrieval.search.duration")` listened for `[:pramana, :retrieval, :search, :duration]` — a non-existent event. Only the two metrics that explicitly set `event_name: "pramana.guard.check"` and (pending fix) actually matched.

**LiveDashboard showed no data for any domain event since the PramanaWeb.Telemetry module was first created (2026-08-29).** Six of eight domain metrics: retrieval duration, retrieval results, guard duration (summary, not the counter), MCP tool calls, bake work duration, and acquisition fetch bytes.

## Change

`apps/pramana_web/lib/pramana_web/telemetry.ex` — added `event_name` to every domain metric:

| Metric | Before | After |
|---|---|---|
| `summary pramana.retrieval.search.duration` | no `event_name` → `[:pramana,:retrieval,:search,:duration]` | `event_name: "pramana.retrieval.search"` |
| `summary pramana.retrieval.search.results` | no `event_name` + no `measurement` → default measurement `:duration` | `event_name: "pramana.retrieval.search"`, `measurement: :results` |
| `summary pramana.guard.check.duration` | no `event_name` → `[:pramana,:guard,:check,:duration]` | `event_name: "pramana.guard.check"` |
| `counter pramana.mcp.tool.calls` | no `event_name` + no `measurement` | `event_name: "pramana.mcp.tool"`, `measurement: :calls` |
| `counter pramana.coverage.caveat.fired` | no `event_name` + no `measurement` | `event_name: "pramana.coverage.caveat"`, `measurement: :fired` |
| `summary pramana.bake.work.duration` | no `event_name` | `event_name: "pramana.bake.work"` |
| `summary pramana.acquire.fetch.bytes` | no `event_name` | `event_name: "pramana.acquire.fetch"` |

The two metrics already correct were left untouched:
- `counter pramana.guard.check.duration` — already had `event_name: "pramana.guard.check"` and `measurement: :duration`
- `summary pramana.coverage.caveat.fired` — already had `event_name: "pramana.coverage.caveat"` and `measurement: :fired` (though the unqualified summary needs its own explicit `event_name` separately)

Counters also received explicit `measurement` since without it they default to event counts rather than summing the relevant measurement key.

## Root cause

The event-name auto-derivation convention in `Telemetry.Metrics` (`metric_name` → `event_name` by replacing `.` with `:`) means a metric name like `"pramana.retrieval.search.duration"` produces event `[:pramana, :retrieval, :search, :duration]` — **four** segments appended to the Phoenix-generated `phoenix.*` suffix convention. But the actual domain events use **three** segments (`[:pramana, :retrieval, :search]`). The mismatch went unnoticed because:

1. No reporter was attached (ConsoleReporter commented out in the template)
2. LiveDashboard showed only Phoenix/VM/DB metrics, which are generated correctly by `phoenix.*` and `pramana.repo.*` conventions
3. The domain metrics section showed flat zeros, which read as "no activity yet" rather than "no activity ever"

## Residual risk

- **No integration test for metrics assembly** — `PramanaWeb.Telemetry.metrics/0` returns a list of metric structs whose correctness depends on runtime event matching. A regression (new metric without `event_name`) would silently collect nothing again. Adding a test that attaches a reporter and emits the expected events would catch this.
- **The `summary pramana.coverage.caveat.fired` metric has the wrong name** — it says `.fired` but it's a `summary`, not a counter. The correct _counter_ for caveats was already present in the same block (`counter pramana.coverage.caveat.fired` before the fix). This is cosmetic — the summary and its counter now point at the same event, so both will collect data. A future session may want to drop the summary and keep only the counter for this signal, which is a count, not a duration.
